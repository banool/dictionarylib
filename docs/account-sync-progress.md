### Offline first: the availability sweep (Daniel, 2026-10-29)

The coordinator's sweep of the client for "nothing waits for the network" and Daniel's ask for tests that play with the backend's availability (plan sections 5.2 and 5.13 updated to match). Fixed:

- List operations pre-empt a sync cycle instead of waiting for it: every network await of a cycle (`_send`, the merge's `/state` calls, `syncAll`, follows) goes through `_net`, which `exclusive` breaks the moment a list operation starts waiting; the step is abandoned, the late answer dropped unapplied, and the cycle runs again after the operation. The black-hole tests found a second wait the sweep didn't list: deleting a linked list took the engine's per-list lock, which a black-holed `/sync` holds for its whole timeout, so `dropOwned` no longer takes it, and a flush (or a subscriber pull) whose answer arrives after its list was dropped discards it.
- Backoff: network and server failures double from 2 s to 5 minutes (was an hour). The retry timer now kicks with a reason of its own (`retry`): it used to kick `resumed`, which (now that `resumed` resets the backoff, as asked) would have retried every 2 s for ever. A `localChange` kick while a retry is pending rides the retry; `resumed`, `startup`, `pullToRefresh` and `signedIn` reset the backoff and go at once; a cycle that finds itself paused (Retry-After) makes sure a retry is due when the pause ends, and a successful cycle clears a stale retry timer. Ops the account answers `retry` back off to 5 minutes too.
- Account-sync requests time out after 30 s (list requests keep 10 s).
- The engine's "changed while you were offline" notice is raised only for a shared list with at least one editor.
- Sign-out never waits: what is queued (list ops, account ops, up to 40 answer batches) is captured with the session, the device signs out at once, and the capture is sent in the background with that session (`PartingFlush`), best effort.
- Server: a `delete` whose (clamped) time is older than the list's newest edit is `applied` as `stale` and the list stays, so edits newer than a delete win whichever device comes back first; the deleting device then gets the list back from the directory.
- Audit of what a background cycle can show: account sync raises only "now syncing" after the merge; the engine raises `sessionExpired` (with the resume banner), `listFull`/`listFullPrivate` (a sign the person just saved didn't fit), `removedAsEditor` (another person's action) and the narrowed `snapshotCatchUp`. Nothing shows for a network, server, kill-switch or timeout failure; the Settings status line is the only place.

Tests: `test/sharing/_fake_time.dart` (fake time with sync's clock following it; `instant` fails if an operation let the clock move), a `NetworkSwitch` on the in-memory server (`up`, `down`, `blackhole`, `flaky`, `slow`, `lossy`), and `test/sharing/account_sync_availability_test.dart` with scenarios a to l (17 tests: first sign-in with the backend down; down after each of the merge's 36 requests and back; a long offline session; `lossy` for every op type; `flaky` converging within 200 requests and a dead hour costing fewer than 150 requests; black-holed create, save, rename, reorder, delete, revision session, random session, setting and sign-out each completing without the clock moving; coming back by resume, the retry timer within five minutes, pull to refresh, and a local change that waits for the timer; two devices offline on one list in both orders; delete against offline edits in all four orders and timings; session expiry found on return; the kill switch on and off; list operations during a black-holed merge). `account_sync_offline_widgets_test.dart`: My lists (create, rename, delete) and a list page (remove a sign) with a cycle stuck in a black hole, each showing after zero-length pumps. `dictionarylib_test_support/lib/net_proxy.dart`: an HTTP proxy with the same modes (down closes the listener, blackhole holds requests, lossy forwards and drops the answer), used by `account_sync_availability_real_test.dart` (scenarios a, c, d and the four of i against the real Worker) and by the on-device pair `runSoloOfflineOnline`/`runSoloOfflineOnlineAfter` (stubs in both apps, in appci's driver as `solo-offline-online` and `solo-offline-online-after`). ## Deviations from the plan

Each with its reason.

1. Account DO `op_log` has an extra `result TEXT` column, and a replayed op answers `duplicate` with the first application's `result`. Without it a `createList` that matched an existing list by name, whose response was lost, could not tell the device which list it matched.
2. `createList` takes an optional `nameMatch: false`. The plan's server-side name match would match a list this device already linked to another of its lists (its default "Pets" and a second local "Pets"), contradicting "two lists called Pets". The device resends with `nameMatch: false` and a fresh request id when the match is a list it already has.
3. The account DO serialises every RPC with an in-memory mutex. A DO's input gate does not hold while it awaits another DO, so without it two concurrent `createList "Animals"` calls interleave at the list DO's `init` and both create (the unit race test fails without the mutex).
4. `missedOps` expands an `addEntries` row into one `addEntry` per video at the same seq. The plan says no old build ever receives `addEntries`, but an old build can own a list that a new device later made private (stop sharing) and then merged into; old builds skip unknown op types and would silently miss those videos.
5. `addEntries` at the 5000 cap applies what fits and answers `applied` with `reasonCode: 'list_full'` (and `rejected list_full` when nothing fits); the op log records only what went in, so `missedOps` is exact. Malformed items in an `addEntries` or `addReviews` op are skipped and counted rather than refusing their good neighbours (`addReviews` reports `invalid`).
6. `unlink` of a list missing from the directory: when the list DO is live and the caller owns it, the row is put back (live) and `still_live` answered. With the plan's rule a device that finds a linked id missing would delete its local copy; this matters after a PITR rewind of an account DO. The app will treat "missing" by sending `unlink` and deleting only on `applied` (Phase 2).
7. `ListDO.purge(ownerUserId, origin)` checks the stored owner (defence in depth: a directory row naming someone else's list cannot destroy it); `wipe` treats `FORBIDDEN` like `NOT_FOUND` (done).
8. `POST /v1/lists` refuses `visibility: 'private'`: a private list made there would be in neither the directory nor the owner index, unreachable from every device.
9. `PUT .../visibility`, `POST .../restore` and the legacy-DELETE "make private" answer 500 when the follow-up `noteVisibility`/`noteRestored` on the account DO fails, so the client retries (the list DO step is then a no-op); otherwise a list could end up private but missing from the directory. `noteRename` and `noteDeleted` failures are logged only (the first only feeds name matching; the second self-heals through `unlink` on the next 410).
10. Legacy DELETE: if `hasDirectory()` throws, the Worker takes the "make private" path, the one that can't lose anything.
11. Account deletion: lists only in the owner index are tombstoned (30-day purge alarm), as the plan says. I first purged them on the spot, but that turns the 410 today's builds act on at once into three 404s, and the unchanged `multi_device_sync_test.dart` at `HEAD` failed; reverted to the plan.
12. A private list mints no invites (`createInvite` answers 403), and `acceptInvite` on a private list answers 403: a private list has no editors.
13. Extra op `reasonCode`s beyond the plan's six: `invalid`, `not_found`, `unknown_type`, `follow_limit`, `forbidden`. An unknown op type is rejected on its own (forward compatible); a malformed envelope (no op id) fails the batch with 400 before anything applies.
14. Paging: the response has `nextSinceSeq` (what the device saves) besides `seq`, and a page always ends on a whole op, because every answer one `addReviews` stores shares a seq and a page cut mid-op would skip the rest of that op for good.
15. Request bodies stay capped at 64 KB. The plan's arithmetic ("a 5000-sign list is 25 ops in one request, well under 64 KB") is off: 25 `addEntries` ops of 200 videos are about 300 KB, and 50 `addReviews` ops of 500 far more. The app must batch list `/sync` and account requests by encoded size as well as by count (Phase 2 and 3).
16. `restore_do.ts` also takes `--bookmark`, so the undo bookmark a restore prints can take it back.

70. Sharing a list under a new name (`PUT .../visibility` with `displayName`) counts as a rename made at the server's time, like the old PUT rename.
71. A delete whose time is unknown (`deletedClientTs` null: a row marked deleted by `unlink`, nobody knowing when) counts as older than any unsent edits, so they restore the list; a tie to the second restores too. Both keep data where the plan's rule can't decide.
72. If the list turns out live on the account when the device thought it gone, the device un-orphans it and never deletes it. A restore the account refuses (purged meanwhile) leaves the list here as a list of its own, linked again by name. An orphaned list with no verdict on its way (the app died between the two steps) is settled from the directory on the next cycle.
73. A rename made while a list was being linked is detected by a `renamed` flag on the linking record (set when the key moves) and sent only when the local name differs from the server's after normalisation; the plan says "with a different server name".
74. The rename dialog no longer retries with a network spinner: there is no request to retry.
75. The too-large subtitle is worked out from the list itself (signed in with account state, not linked, over the cap), so it goes the moment the list is small enough; "Only on this device" stays for the other reasons (account full, a name the account refused). The too-large text is kept, renamed `listTooLargeToSyncBody`, for the share dialog's refusal (the plan's "existing too-many-entries dialog").
76. `dart fix --apply` was run on `lib/l10n` only (nothing to fix there): on the whole package it would also change two unrelated lint findings that are in the baseline.
77. Accepted: the directory's cached name can stay old if the app dies between queueing the list's rename and the account's (one meta write, then one state write). It only feeds name matching; the list's own name, which every screen shows, is right.

From the availability sweep (2026-10-29):

78. Sign-out sends its parting flush in the background after signing out (plan 5.9: a best-effort flush of up to 10 s first), so signing out never waits for the network; if the flush fails, the work is on the device and the next sign-in's merge takes it up.
79. The server refuses (as `stale`) a delete older than the list's newest edit, beyond the client-side rule of section 5.5, so the timestamp rule holds when the edits reach the account before the delete does.
80. The engine's per-list lock no longer covers dropping a wrapper (`dropOwned`), and late answers for dropped lists are discarded; the sweep listed only the controller's lock.
81. `removedAsEditor` still shows a snackbar from a background sync: it tells the person someone else removed them from a list, not that sync had trouble.
82. Following a list can't be done offline (it needs the list's contents from the share link), so the long offline session unfollows offline and the follow is exercised under `lossy` with the list fetched first.
83. The black-hole acceptance test fails on the code before the fix with the operation waiting for the request's 10 s timeout, rather than hanging: in fake time the timeout fires.

Accepted, not fixed (rare, and no data lost): a random session can be counted twice if pending ops reach a new account incarnation before the device notices it changed (an account deleted on one device, then signed into again on another that had queued sessions), or if the same install signs in again more than 120 days after a reset (its initial-count op id has left the account's op log). The real-Worker test files can't share one `flutter test` run (Test runs).

Considered and kept as the plan has it: account deletion purges shared lists in the directory on the spot, so their old-build editors see three 404s rather than an immediate 410 (the plan accepts this); lists only in the owner index are tombstoned as before.
