## Deviations from the plan

Each with its reason.

1. Account DO `op_log` has an extra `result TEXT` column, and a replayed op answers `duplicate` with the first application's `result`. Without it a `createList` that matched an existing list by name, whose response was lost, could not tell the device which list it matched.
2. `createList` takes an optional `nameMatch: false`. The plan's server-side name match would match a list this device already linked to another of its lists (its default "Pets" and a second local "Pets"), contradicting "two lists called Pets". The device resends with `nameMatch: false` and a fresh request id when the match is a list it already has.
3. The account DO serialises every RPC with an in-memory mutex. A DO's input gate does not hold while it awaits another DO, so without it two concurrent `createList "Animals"` calls interleave at the list DO's `init` and both create (the unit race test fails without the mutex).
4. `missedOps` expands an `addEntries` row into one `addEntry` per video at the same seq. The plan says no old build ever receives `addEntries`, but an old build can own a list that a new device later made private (stop sharing) and then merged into; old builds skip unknown op types and would silently miss those videos.
5. `addEntries` at the 5000 cap applies what fits and answers `applied` with `reasonCode: 'list_full'` (and `rejected list_full` when nothing fits); the op log records only what went in, so `missedOps` is exact. Malformed items in an `addEntries` or `addReviews` op are skipped and counted rather than refusing their good neighbours (`addReviews` reports `invalid`).
6. `unlink` of a list missing from the directory: when the list DO is live and the caller owns it, the row is put back (live) and `still_live` answered. With the plan's rule a device that finds a linked id missing would delete its local copy; this matters after a PITR rewind of an account DO. The app will treat "missing" by sending `unlink` and deleting only on `applied` (Phase 2).
7. `ListDO.purge(ownerUserId, origin)` checks the stored owner (defence in depth: a directory row naming someone else's list cannot destroy it); `wipe` treats `FORBIDDEN` like `NOT_FOUND` (done).
8. `POST /v1/lists` refuses `visibility: 'private'`: a private list made there would be in neither the directory nor the owner index, unreachable from every device.
9. `PUT .../visibility`, `POST .../restore` and the legacy-DELETE "make private" answer 500 when the follow-up `noteVisibility`/`noteRestored` on the account DO fails, so the client retries (the list DO step is then a no-op); otherwise a list could end up private but missing from the directory. `noteRename` and `noteDeleted` failures are logged only (the first only feeds name matching; the second self-heals through `unlink` on the next 410).
10. Legacy DELETE: if `hasDirectory()` throws, the Worker takes the "make private" path, the one that can't lose anything.
11. Account deletion: lists only in the owner index are tombstoned (30-day purge alarm), as the plan says. I first purged them on the spot, but that turns the 410 today's builds act on at once into three 404s, and the unchanged `multi_device_sync_test.dart` at `HEAD` failed; reverted to the plan.
12. A private list mints no invites (`createInvite` answers 403), and `acceptInvite` on a private list answers 403: a private list has no editors.
13. Extra op `reasonCode`s beyond the plan's six: `invalid`, `not_found`, `unknown_type`, `follow_limit`, `forbidden`. An unknown op type is rejected on its own (forward compatible); a malformed envelope (no op id) fails the batch with 400 before anything applies.
14. Paging: the response has `nextSinceSeq` (what the device saves) besides `seq`, and a page always ends on a whole op, because every answer one `addReviews` stores shares a seq and a page cut mid-op would skip the rest of that op for good.
15. Request bodies stay capped at 64 KB. The plan's arithmetic ("a 5000-sign list is 25 ops in one request, well under 64 KB") is off: 25 `addEntries` ops of 200 videos are about 300 KB, and 50 `addReviews` ops of 500 far more. The app must batch list `/sync` and account requests by encoded size as well as by count (Phase 2 and 3).
16. `restore_do.ts` also takes `--bookmark`, so the undo bookmark a restore prints can take it back.

From the independent review of Phase 1 (fixed in 6c8fadb):

17. Account deletion leaves the deletion time in the account DO (`meta.wiped_at`), and `POST /v1/account/sync` answers 401 to sessions issued before it (the session JWT's `iat`, now carried in `CallerIdentity.issuedAt`). Without this another device still holding an old session (sessions can't be revoked) would re-create the account and re-upload everything after the person deleted it. Responses also carry an `incarnation` id that changes with a deletion; a device that sees it change drops its links (keeping every list) and merges again (Phase 2).
18. `resetProgress` clamps its time to the server clock plus five minutes: a device whose clock runs a year fast would otherwise set a cut-off that refuses every real answer from every device for a year.
19. The purge alarm and `purge()` run under `blockConcurrencyWhile` with `deleteAll()` before any non-storage await, so a restore can't land between the check and the delete and be undone (alarms run alongside requests). `purge()` fails, keeping everything, when the public snapshot can't be removed, so a deleted account can't leave a public copy behind.
20. `setVisibility` holds the input gate across its R2 work, removes the public snapshot first and fails if it can't, and a repeat (unchanged visibility) runs the R2 half again, repairing a half-finished flip. The plan said an unchanged visibility is a no-op.
21. The legacy DELETE records the list in the directory (`noteVisibility`, with the name from `/state`) before making it private, not after; otherwise a failure between the two could leave a list shared from an old build, and not yet reconciled, in no index at all.
22. Reconciliation removes owner markers whose list is gone (`NOT_FOUND`/`GONE`), or every sync would ask about them again.
23. The account op log keeps the last 120 days of ops (at least 500, at most 20,000) rather than the plan's 500, because a replay outside the log is not harmless for every op (a `delete` re-sent after a restore would delete again) and each `addReviews` batch is an op.
24. `createList` with the request id of a list since deleted answers `id_collision` (fresh ids); `creating` rows nobody finished are dropped after a week.
25. A `DELETE` with the capability header refuses the default list (403), as the `delete` op does.
26. `RUNBOOK.md`: once `AccountDO` is deployed, `wrangler rollback` to a version before it is refused by Cloudflare, and the brakes are the kill switch, the knob and a forward fix.

From Phase 2:

27. Owner-list "gone" (410 or three 404s) is not acted on locally at once: the engine stops syncing the list (orphaned), the controller queues a verifying `unlink`, and the local copy goes only when the account confirms it gone (kept, as `kept_unsent`, if it had unsent changes). The plan acts on a 410 immediately. Waiting for the verdict also avoids a deadlock: the engine calls the hook under the list's lock while a cycle holding the controller lock may be waiting for that list.
28. A linked list missing from the directory (not marked deleted) is never deleted on that evidence: it gets an `unlink` (see 6), and the account puts the row back if the list is live.
29. `EntryList.addVideo`/`removeVideo`/… on a plain list that has an owner wrapper hand the change to the wrapper instead of tripping `_assertNotOwnerShared`. Account sync links lists in the background, so a screen can hold the plain list from before the link; without this the change would stay local and never reach the server. The assert stays for the remaining direct paths.
30. Restore detection uses a prefs flag (`install_marker_written`) as well as the marker: the plan's rule ("a stored client id and no marker") would count every upgrading person who has used sharing as a restore on the first launch of this build. "Flag present, marker missing" is a restore. iOS keychain accessibility is `first_unlock_this_device` (same "this device only" property as the plan's `unlocked_this_device`, but also readable in a launch before the first unlock, which would otherwise read as a restore).
31. The knob is read in dictionarylib's bootstrap in the background (not through the apps' `extraStartupTasks`), so both apps get it without app changes and the first frame never waits for it; the controller reads the cached prefs value.
32. When the account has no default list and the device's default is already linked (a list it shared before account sync, which the merge doesn't recreate), the device sends `setDefault` for it. Otherwise another device's merge would create a new default and this device's default pointer would move to that.
33. The merge's and links' account calls ask for no answers (a `sinceSeq` beyond any seq), so they don't drag pages of history along; answers are paged only by the steady-state round trip.
34. Sharing with account sync switched off (knob) falls back to the old create-and-upload (`POST /v1/lists`), which reconciliation later brings into the directory; with account sync on it links the list (running a cycle if needed) and flips its visibility. Stopping a share is always the `PUT .../visibility` to private, never a `DELETE`.
35. Settings' status line also has "Synced {n} hours ago" and "Synced {n} days ago" (the plan's copy has minutes only).
36. A list made private keeps the name it was shared under (sharing applies the share dialog's name as a rename on the account). Before account sync, unsharing went back to the local list's name.
37. Renaming a linked list needs the network (it is a `PUT` on the list). The plan says so; it's a change for signed-in people, whose lists were all renamed offline before.
38. `AsyncLock` no longer makes its first future at construction (a future made in one zone and awaited in a widget test's fake-async zone never resumes there; this hung a widget test). No behaviour change in the app.
39. The sign-in dialog's title stays "Sign in to share" (only its body changed, as the plan says), which reads a little oddly when signing in from Settings.
40. The on-device phases run one device at a time, as the driver's other phases do: `flutter test integration_test` installs the app afresh for every run and removes it afterwards. Phase E is three runs (A, then B, then A again as a new install), so the two devices sign in one after the other, not "within seconds of each other"; the concurrent case is covered by the backend's race test, the in-process two-device tests and `account_sync_multi_device_test.dart` (two full client stacks against the real Worker). In F and G "the other device" is played by the suite over HTTP as the same person (`MdOtherDevice`), the way another phone's app would talk to the Worker.
41. The device-restore check from 5.13 (copy one simulator's app container into a fresh install) was not run on a device. Restore detection is covered by unit tests (fresh install, upgrade, restored) only.
42. The upgrade suite (`upgrade_shared_favourites_suite.dart`) now waits for the account merge and clears its snackbar before opening the Revision tab: the "now syncing" snackbar covered the Start button.

From Phase 3:

43. Settings changes are found by comparing each synced setting with the value last known to be in sync, at the start of every account round trip and when the app goes to the background, not by routing writes through a `syncedSettings.set`: the apps write the region settings straight to prefs, so a setter would miss them. An incoming value is applied neither over a pending `setSetting` nor over a change made here since the last look.
44. `ReviewHistory.reset(tsUs)` drops unsent answers from before the cut-off but keeps later ones queued. The plan clears the whole queue, which would lose this device's answers made after a reset made elsewhere.
45. `appendLocal` writes the unsent queue before the history (a kill between leaves the answers queued, and they come back from the account), and bumps `version` too, so pages showing the history refresh after a session as well.
46. The merge's history step adds the stored history to the upload queue rather than replacing the queue, so answers queued but not stored (a kill inside `appendLocal`) stay.
47. Random mode: the device's count goes up at the merge as one session with op id `random-initial-<client id>`, so signing out and in again on the same install doesn't count it twice (while the account's op log, 120 days, holds that id). Sessions before the merge is done go into the count, sessions after it are ops of their own. A random session done signed out between two sign-ins on one install doesn't reach the account (the second sign-in's count op is a duplicate).
48. A reset made on the account before the device joined it (at its merge) is recorded as seen and not applied to the device: its older answers stay on it, and the account refuses them. The plan applies any reset time greater than the last seen one, which would delete a joining device's history because of a reset that was never about it.
49. "Delete all revision progress" queues the account's `resetProgress` first, then resets the device, and doesn't mark the reset as seen: the account's answer applies it again (dropping nothing more), so a kill between the two still resets the device.
50. Incoming setting values are checked per key before they are stored: the right type, the revision strategy index in range, the card limit one the Revision page offers (`revisionCardLimitOptions`, now shared with the page), region values numeric. A value this build can't use stays on the account and the device keeps its own without sending it over that. Without this a value from a newer build could break the Revision page here.
51. `AsyncLock` now drops its future once idle (the global history lock's future, made in one widget test's zone, hung the next test).
52. `readReviews()` stays, as a one-line call to `reviewHistory.read()` (the suites use it). `migrateLegacyReviewsIfNeeded` still writes `stored_reviews` directly: once, at start-up, before account sync can run.
53. Answers a device uploaded come back to it in later pages (the account doesn't record which device sent what) and are deduplicated there; the cost is one download of its own answers.
54. Phase H's first run seeds two cards as learned through `recordAnswers` (as earlier sessions would have) before a real session on the rest, and the due-count checks compare with the same cards and no history, because Auslan's region filter decides which saved signs become cards.
55. `upgrade_sync_from_old_install_suite.dart` runs two ways: by default it writes the old storage layout itself (as `upgrade_shared_favourites_suite.dart` does); with `--dart-define=MD_UPGRADE_FROM_INSTALL=true` it takes what an old build installed on the device left there, which is how the old-build-then-new-build check ran (Test runs). The suite also clears a leftover session first: on iOS the keychain outlives the app.
56. New dependencies: `crypto` in dictionarylib (already in both apps' lockfiles), `dolphinsr` in `dictionarylib_test_support` (to build answers).

From an independent review of the Phase 2 and 3 client (a separate agent read `e30e835..ec62438`; every finding below was checked against the code, fixed, and given a test that fails without the fix):

57. Work done while the session has expired is queued for the account (answers, random sessions, a reset, reorders, deletes, follows), not dropped: it goes up when the same person signs in again (`queuesForAccount`: a state exists, isn't being cleared, and no other account is signed in; also true with the knob off). Before, those answers never reached the account, since the merge doesn't run again for the same account.
58. Ops the account keeps answering `retry` (an unreachable list DO, say) are sent again after a doubling wait (30 s to an hour), not in a tight loop of requests.
59. A server restored to an earlier point (the device's cursor ahead of its seq) is now read again from the start, and every answer is queued again; before, the reset cursor was overwritten in the same step.
60. Sign-out marks the state `clearing` before the first wrapper goes; a kill part way is finished at the next cycle (which, still signed in, merges again by name) instead of installing the account's lists beside the local ones that had lost their links.
61. Deleting a linked list queues the account's delete, then deletes the local list, then drops the wrapper; deleting a list mid-link deletes the local list first and queues the account's delete with forgetting the record; a record whose local list has gone queues that delete. Before, a kill in between could leave a local list without its link, which linked again and brought the list back everywhere.
62. The engine's "owner list gone" hook says whether it handled it; without account state (signed out, the knob off from the start) the engine falls back to the old behaviour (a plain local list) instead of re-syncing a dead list forever. With account state it waits for the account's verdict, and the list stays editable meanwhile (an orphaned owner wrapper takes edits, which either sync once it's found live or keep it on the device as unsent changes); before, edits made then were dropped.
63. With the knob off, sharing a list already on the account flips its visibility instead of making a second list.
64. The merge sends a random-mode count above the account's per-session cap (10,000) in pieces, each with its own stable id.
65. Signing out also sends queued answers in its 10-second window, and clearing the queue first stores any answers in it the history lacks (a kill inside `appendLocal`).
66. A live directory row whose list has gone is sent an `unlink` (the account marks it deleted) rather than matched again on every pass. Lists kept on the device for size, or because the account was full, are tried again once that has passed; a list whose create the account refused is marked `refused` and tried again after a rename.
67. Uploaded answers leave the queue ten batches at a time (each queue write rewrites the prefs file on Android; a kill re-sends those batches, which the account finds to be duplicates), and pages of incoming answers notify the Revision pages once per round trip, not per page.
68. A random-mode session ending during the merge is decided and counted without an await in between, so it is in the counter the merge sends or an op of its own, never neither. A revision-list selection naming a list not yet installed is applied again once it is.

Accepted, not fixed (rare, and no data lost): a random session can be counted twice if pending ops reach a new account incarnation before the device notices it changed (an account deleted on one device, then signed into again on another that had queued sessions), or if the same install signs in again more than 120 days after a reset (its initial-count op id has left the account's op log). The real-Worker test files can't share one `flutter test` run (Test runs).

Considered and kept as the plan has it: account deletion purges shared lists in the directory on the spot, so their old-build editors see three 404s rather than an immediate 410 (the plan accepts this); lists only in the owner index are tombstoned as before.
